Real bug this shape caused Pre-1990s drivers have no 3-letter code (comes through as literal "\N"). A naive merge on that column collapses dozens of different people onto one join key, multiplying rows combinatorially. Fixed by filtering to year >= MULTI_CIRCUIT_MIN_YEAR (2008) before any merge — the builders still see the full timeline for debut-year lookups, but the exploding join never happens.

3.Feature engineering — leakage-safe by construction

Every feature answers "what did we know before this race started?" — enforced structurally, not by a rule someone has to remember.

FeatureLeakage guard
driver_standing_beforecumsum() - points — subtracts the row's own points before ranking
driver_circuit_avg_finish.expanding().mean().shift(1) — shift excludes the current row
driver_recent_form.rolling(3).mean().shift(1) — same shift
constructor_recent_formsame rolling+shift, aggregated across both cars first
pipeline.py
def build_season_form(raw: dict) -> pd.DataFrame:
    full["driver_points_before"] = (
        full.groupby(["year", "driverId"])["points"].cumsum() - full["points"]
    )
    full["driver_standing_before"] = (
        full.groupby(["year", "raceId"])["driver_points_before"].rank(method="min", ascending=False)
    )

def build_recent_form(raw: dict) -> pd.DataFrame:
    full["driver_recent_form"] = (
        full.groupby("driverId")["position_num"]
        .transform(lambda s: s.rolling(RECENT_FORM_WINDOW, min_periods=1).mean().shift(1))
    )

Because every builder is already strictly pre-race, this same code predicts a race that hasn't happened — see §5.

Dropped despite being predictive

grid_position correlates strongly with finishing position but doesn't exist until qualifying — usually about a day before the race. Kept out of FEATURE_COLUMNS on purpose, trading ~4pp accuracy for being usable the moment the previous race ends rather than only the day before the next one.

4.Model selection & training

  • Clean — drop rows missing any REQUIRED_COLUMNS or the target.
  • Chronological split — most recent seasons held out as test, not a random shuffle. A random split would let the model be judged on data chronologically before some of its own training rows.
  • Balance — upsample the minority class, after the split, on the training fold only (upsampling before the split risks a duplicated row landing in both train and test).
  • Compare 4 candidates — Random Forest, Logistic Regression, SVM, HistGradientBoosting — each baseline vs. GridSearchCV-tuned.
  • Refit winner on everything — train+test years combined, since the shipped model should use every real result available.
    • pipeline.py — chronological_split
    def chronological_split(df, test_size=0.25, test_circuit_id=None):
    eval_scope = df if test_circuit_id is None else df[df["circuit_id"] == str(test_circuit_id)]
    # walk backward from the newest year, accumulating rows until ~25% held out
    test_years, running_total = [], 0
    for year in reversed(year_counts.index.tolist()):
        if running_total >= n_test_target: break
        test_years.append(year); running_total += year_counts[year]

    Two training runs happen every time pipeline.py executes, and whichever generalizes better gets exported:

    RunTrained onEvaluated on
    Singapore-onlySingapore GP, every yearheld-out recent Singapore years
    Multi-circuitevery circuit, 2008+held-out years, Singapore rows only (test_circuit_id) — tests "does training everywhere help predict here"

    Multi-circuit has won every run so far (0.820 held-out accuracy on the current points-finish target, HistGradientBoostingClassifier) and is what's actually deployed.

    5.The "hypothetical race" trick

    How a model trained only on results predicts a race with no result yet.

    Because every feature builder is already strictly pre-race (§3), a placeholder row — real driver, real constructor, real circuit, position = "\N" — run through the same builders yields exactly the features that race would have had. Nothing from the future leaks in, because there is no future in the row.

    webapp/predictions.py
    def upcoming_features(self, circuit_id, entrants, year, round_):
    placeholder_results = pd.DataFrame([
        {"raceId": race_id, "driverId": code, "constructorId": constructor,
         "position": NO_RESULT, "points": 0}
        for code, constructor in entrants
    ])
    scoped = {"results": pd.concat([self.combined["results"][cols], placeholder_results]),
              "races": pd.concat([self.combined["races"], placeholder_race])}
    return self._apply_builders(scoped)   # same 4 builders as training, unmodified

    Where "next race" always slots in: immediately after the last completed race, regardless of which circuit is being asked about.

    Real bug this caught Slotting a placeholder into a season with zero completed races ties every driver's driver_standing_before at P1 (everyone's cumulative points are 0) — silently destroying the model's strongest feature and leaving it to guess from circuit history alone. Fixed: features are always computed at next_round_slot() (the real "day after the last race" position), and only the label shown to the user reflects which future round was actually asked about.

    7.Anatomy of one request

    GET /api/predictions/upcoming?circuit=monza, end to end:

  • main.py route handler calls service.latest_entry_list() — the 20 (driver, constructor) pairs from the most recent race.
  • service.next_round_slot() — reads race_catalog(), returns (year, last_round + 1).
  • service.predict_upcoming(circuit, entrants, year, round_) — memoized via @functools.lru_cache, keyed on all four args.
  • Cache miss → upcoming_features() builds the placeholder row, runs the 4 feature builders (§5).
  • model_store.predict_points_proba(features) — model.predict_proba(features)[:, class_1_index].
  • _to_rows() sorts by probability descending, marks predicted_points = position < 10 (rank-based, not a 50% cutoff — see §12).
  • Response JSON assembled with reference.driver() / .team() for display names.

    • 8.The auto-update pipeline — the coordination core

    A daemon thread, started once at import time, living inside the same uvicorn process — not a cron job, not a separate service.

    webapp/scheduler.py
    def _loop(self):
    while not self._stop.is_set():
        self.check_now()
        self._stop.wait(CHECK_INTERVAL_SECONDS)   # default 3 hours
  • Check — live.refresh_season(year) fetches that season from Jolpica, diffs row count against data/multi_circuit_fresh.csv.
  • Publish immediately — if changed, rebuild_service() runs before retraining. Predictions reflect the new race's standings/form within seconds; the model's learned weights lag until step 4.
  • Retrain as a subprocess — subprocess.run([sys.executable, "pipeline.py", ...]), not an in-process call: a ~20-30 min GridSearchCV sweep would otherwise stall the event loop, and a crash there can't take the API down.
  • Atomic swap — os.replace(tmp_path, model.pkl), then model_store.reload(). Every component already holds a reference to the same ModelStore object, so overwriting .model inside it is visible everywhere instantly — no restart.
    • def check_now(self, force=False):
    if not self._busy.acquire(blocking=False):
        return {"ok": False, "busy": True}     # scheduled + manual can't race each other
    ...
    if result.get("changed"):
        self.rebuild_service()               # step 2 -- fast
        self.last_data_refresh = time.time()
    self._retrain()                          # step 3+4 -- slow

    Why a subprocess, concretely

    os.replace(tmp_path, self.model_store.path)   # atomic on same filesystem --
                                               # a request mid-swap sees either the
                                               # whole old file or the whole new one,
                                               # never a partial write
self.model_store.reload()
self.rebuild_service()                        # feature tables were built pre-retrain, redo them

    9.Crash-safety: the fingerprint sidecar

    "Did a fetch change anything?" isn't enough on its own — it can't recover from an interrupted retrain.

    The failure mode this fixes Server restarts mid-retrain (deploy, laptop sleep) → new race data already on disk, model never replaced. Next boot asks "did the last fetch add rows?" — no, they're already there — and never retrains again, silently staying one race behind forever.
    webapp/scheduler.py
    def _data_fingerprint(self) -> str:
    frame = pd.read_csv(fresh_csv_path, usecols=["year", "round"])
    latest = frame.sort_values(["year", "round"]).iloc[-1]
    return f"{latest.year}_{latest.round}_{len(frame)}"

def model_is_stale(self) -> bool:
    return self._data_fingerprint() != self._trained_fingerprint()   # reads model.pkl.meta.json

    Written only after the swap succeeds — a fingerprint recorded before the model actually landed would mark an interrupted retrain as done:

    fingerprint_at_start = self._data_fingerprint()
... subprocess.run(pipeline.py) ...
os.replace(tmp_path, self.model_store.path)
self._record_trained_fingerprint(fingerprint_at_start)   # only now

    model.pkl.meta.json is gitignored — it describes one machine's local model, and committing it would tell a fresh clone the checked-in model.pkl is current when it almost certainly isn't.

    Why one season, not all of them

    driver_standing_before and the rolling-form features are within-season quantities — a championship position only means something relative to the season it was computed in. Pooling 2008–2025 would average across grids that share no drivers, cars or regulations, and a reader consulting analytics to reason about the next race wants this year's competitive order.

    Two definitional decisions worth copying

    def _scored(frame):
    # NaN, not False, for a DNF -- excluded from every rate rather than
    # silently counted as a failure, which conflates "wasn't fast enough"
    # with "didn't finish".
    return frame["actual_position"].between(1, pipeline.POINTS_POSITIONS)

# Quantile buckets, not equal-width: championship standing is uniform but
# circuit-average-finish clusters hard, and equal-width bins there produce
# near-empty extremes whose rates swing on two or three drivers.
binned = pd.qcut(usable[feature], q=buckets, duplicates="drop")

    Charts: hand-rolled SVG, real pixels

    No charting library — same no-build-step stance as the rest of the frontend. Charts are drawn in pixel coordinates measured off their container rather than in a viewBox scaled to fit, because a stretched viewBox shrinks the tick labels along with the bars.

    Real bug this shape caused An auto-fit grid gives its first child the whole row until siblings arrive. Measuring each small multiple as it was appended read a width that cell would not keep — so preserveAspectRatio letterboxed chart #1 down to a third of its intended height, labels and all. Fixed by building every cell first, then measuring: 
    // pass 1: build and append, measuring nothing
const cells = distributions.filter((e) => e.counts.length).map((entry) => {
  const plot = el("div"); cell.appendChild(plot); container.appendChild(cell);
  return { entry, plot };
});
// pass 2: the grid has settled, so clientWidth is now the real column
cells.forEach(({ entry, plot }) => { const width = chartWidth(plot, 240); ... });

    Colour follows the job, not the entity. One hue for every single-series chart (categories are already named on the axis, so a second hue would encode nothing); a two-hue diverging scale only on the correlation chart, where the sign genuinely is the message. The pair was validated against this app's dark surface rather than assumed — CVD ΔE 19.2, normal-vision ΔE 29.0, both clear of the 8 / 15 floors.

    12.Recurring design patterns

    Rank-based, not threshold-based, classification

    // WRONG -- disagrees with what the sorted-by-probability UI visibly shows
predicted_points = probability >= 0.5

// RIGHT -- a points finish always names exactly POINTS_POSITIONS drivers
predicted_points = position_in_sorted_list < POINTS_POSITIONS

    The threshold version let a borderline driver at rank 10 with 42% probability read as "not predicted" while still visibly sitting in the top-10 rows — a real miss then displayed as "called right" when the driver finished outside the points and the (wrong) prediction also said "no."

    Cache-poisoning-proof caching

    # webapp/images.py's predecessor (removed, see §13) -- the general shape
if not response.ok:
    return miss              # NEVER cached -- a 403 today isn't "no photo forever"
result = {...}
self._cache[title] = result   # only a genuine answer gets remembered

    Paired with a CACHE_VERSION constant bumped whenever a bug could have written bad entries — old-version cache files are discarded wholesale on load rather than trusted.

    Classify by what the reader wants, not by what the source is

    The news tab filters by topic, not by outlet — "show me driver news" is a question a reader has; "show me one site's coverage" is not. Tagging happens server-side on title + summary, and a headline can carry more than one tag:

    webapp/news.py
    CATEGORIES = ["Drivers", "Teams", "Regulations", "Race Weekend", "Other"]

# Keyword sets are seeded from the data the app already has -- current
# grid surnames and team names -- so a new driver is matchable the moment
# the roster refresh picks them up, with no keyword list to maintain.
DRIVER_KEYWORDS = {surname.lower() for _, surname, _ in CURRENT_GRID.values()} | {
    "driver", "rookie", "seat", "signing", "contract", "debut", ...}

def _categorize(title: str, summary: str) -> list:
    text = f"{title} {summary}".lower()
    hits = []
    if any(k in text for k in DRIVER_KEYWORDS): hits.append("Drivers")
    ...
    return hits or ["Other"]   # never silently drop a headline
